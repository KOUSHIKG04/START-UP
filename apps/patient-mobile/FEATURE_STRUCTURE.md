# Patient feature ownership review

Reviewed every source file under `src/features` and its references. This change
organizes existing implementations; native/device verification remains separate.

## Conventions

- `screens/`: navigable composition and screen presentation.
- `components/`: feature UI, including private presentation state and animations.
- `hooks/`: queries, mutations, subscriptions, device effects and workflow coordination.
- `types/`: named feature contracts, with kebab-case filenames.
- `utils/`: pure helpers and flow-specific `*Constants` configuration.
- `services/`: platform/backend integrations with side effects.
- `stores/`: navigation drafts shared between screens.

Create folders only when they contain an implementation. Small private render
helpers and styles may remain with their component. Compatibility type exports
point to the owner rather than defining a second contract. Explicitly named demo
constants remain separate from live schedules, slots and booking results.

## Flow owners

| Feature                           | Responsibilities                                                                                                                                                  |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Ambulance                         | Booking, legacy live booking, SOS, hospital selection and completion have separate hooks. Tracking sections and hospital cards have component owners.             |
| Appointments                      | `useAppointments` owns cancellation and QR issuance. Booking status sections are components; consultation maps and parsing have separate owners.                  |
| Auth                              | Login, OTP, setup, onboarding, family profiles, address selection and profile forms have named hooks. Form conversion, choices and types remain in their feature. |
| Consultations                     | Online join/audio, chat/device controls and completion have hooks. Summary UI and visit title formatting have separate owners.                                    |
| Doctors                           | Search, results, guide and booking have hooks. Category, calendar and route helpers have explicit owners.                                                         |
| Home                              | Home and search coordination have hooks. The search overlay is a component; routes and choices live in utilities/configuration.                                   |
| Locations                         | `useMapPicker` coordinates the map; drafts live in `stores`; geocoding/address resolution live in `services`; formatting and coordinate helpers live in `utils`.  |
| Medicines, prescriptions, records | Each screen's hook retains its query, refetch and feedback behavior.                                                                                              |
| Notifications                     | The device subscription hook is separate from SDK registration, sign-out and local scheduling services. Drawer data uses its existing hook.                       |
| Profile                           | Profile data, PIN and settings have hooks. Contact and action rows have component owners.                                                                         |

## Validation boundaries

Structure checks enforce named-type ownership, configuration boundaries, relative
imports and screen/data separation. Lifecycle checks cover notification disposal
and OTP timers; existing booking, guide, notification and map checks are retained.
The captured legacy map harness had 17 failures before this change, including
checks for other apps. TypeScript had 78 errors before the cleanup. Those baselines
are compared separately from new regressions. Permissions, maps, audio and push
delivery still require native testing.
