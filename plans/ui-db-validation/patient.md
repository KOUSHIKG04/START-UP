# Patient workflow cross-validation

Read-only audit of every patient feature screen/type, route adapter and relevant schema. `features/auth/screens/LoginScreen.tsx` and `OnboardingScreen.tsx` return null. Supabase/location/notification service files are empty. Phone OTP is confirmed by Figma `313:94` and `314:201`; the earlier email-first assumption is rejected. All API names except list_public_practices below are proposed/missing.

## Action chains and missing cross-app edges

1. **Discovery/book:** symptom → doctor/practice → mode → authorized patient → published window → reserve RPC → actor/patient/capacity/price validation → appointment/outbox → doctor/reception inbox → patient result. Current chain stops at demo route navigation and loses patient/reason.
2. **Check in/queue:** token → authorized doctor/reception consume → expiry/scope/replay checks → attendance + ticket transaction → private event → staff queue and patient's own position. Patient local toggle is not an authorization path.
3. **Consult/sign/review:** clinician command → signed immutable records/revision → event → patient records/reminders → eligible review; current patient demo completion cannot become backend authority.
4. **Ambulance/SOS:** normal/guest request → location/capability/quote → atomic offer assignment → arrival → PIN or audited override → tracking → handoff/final quote → verified payment → review. All exception paths must be explicit, including no driver, cancellation, locked PIN, changed destination and payment failure.

## Database → UI

Patient statuses pending/approved omit confirmed's canonical name and completed/rejected/cancelled/no_show/in_consultation. Add explicit lifecycle projection rather than changing all DB states to display labels. Queue awaiting_arrival/called/held/no_show need usable patient messages. Signed/amended/void clinical history, replacement/discontinued prescriptions, phase/interval/PRN schedules, attachment scan state, dependent access revocation, follow-up withdrawn/fulfilled, payment reported/failed/refund and notification failures need UI or a documented backend-only reason.

Never expose token/PIN hashes, issuer/subject, worker leases, raw audit payloads, idempotency internals or other patients' queue identities. Views may carry opaque IDs/row versions without editable UI.
