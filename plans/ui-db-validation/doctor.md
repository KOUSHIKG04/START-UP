# Doctor-mobile UI ↔ database validation

Audit date: 2026-09-23. Read-only source audit; this report is the only artifact written by this auditor. Paths below are relative to `C:/startup`. Line references describe the audited source snapshot, not future implementations.

## Scope, decisions, and alignment standard

Inspected all eleven feature screens: login, home, appointments, schedule, scan QR, clinical notes, prescription, online consultation, home visit, chat, and profile; their route helpers, types, demo source, Zustand store and service placeholders; corresponding Drizzle entities and the three applied migrations. The root audit separately inspected Figma and confirmed **mobile phone OTP**. This report does not claim an independent visual Figma review.

Confirmed product direction from root reconciliation: Supabase-first shared backend; hospital/clinic portal first and platform administration later; aggregate bed counts first; independent and invited ambulance-driver onboarding paths. For doctor-mobile, this means phone OTP is settled, clinic-owner capabilities must work without reception staff, and platform verification operations must remain explicitly assigned even if their full portal is deferred.

The auth SQL at `plans/ui-db-validation/drafts/auth-onboarding.unapproved.sql` is an unapplied draft and is **not deployed or aligned functionality**. It must not be treated as an available API.

An aligned workflow requires screen → authorized API → validation/business rule → database mutation/read → event → affected app refresh. Matching a UI field to a table alone is structural coverage, not functional alignment.

**Result:** no doctor operational workflow is fully aligned end-to-end. Operational data comes from `apps/doctor-mobile/src/data/demo.ts`, component state, or `apps/doctor-mobile/src/stores/useDoctorStore.ts`. `apps/doctor-mobile/src/services/supabase.ts`, `location.ts`, and `notifications.ts` are empty placeholders. Demos are intentionally labeled; the gap is absent integration, not misleading demo labeling. The deployed `public.list_public_practices` is a narrow public read foundation and is not called by doctor-mobile.

The UI `Appointment.status` at `apps/doctor-mobile/src/types/doctor.ts:21` only allows waiting/completed; this must not be reused as the database appointment enum. Appointment, queue, check-in and clinical states are separate axes. A UI display label can be derived from a documented combination but must not overwrite source states.

One identity can be both `doctor.identity_id` and `organization_member(role=owner)`. No receptionist is required. `can_manage_practice`, guards migration :127–143, already recognizes verified own doctors, owners/admins and specifically scoped receptionists for **operational** access. It is not a clinical-record authorization policy. The solo-doctor UI must expose approval, check-in, walk-in and queue controls; otherwise the data model supports the scenario but the product cannot operate it.

## Prioritized findings

### [DOCTOR-01] Implement authorized workflow APIs before replacing demo adapters

- **Evidence:** `apps/doctor-mobile/src/features/auth/screens/LoginScreen.tsx:2` returns null; `apps/doctor-mobile/src/stores/useDoctorStore.ts:46` writes local state; public_directory migration :2 exposes only directory read.
- **Impact:** Doctor actions cannot update patient/reception data or enforce cross-app actor/tenant rules.
- **Effort:** L (multi-day, including permission/concurrency tests).
- **Risk:** HIGH — clinical access and consistency.
- **Confidence:** HIGH.
- **Fix sketch:** Connect confirmed phone OTP, scoped read DTOs and operation-specific transactional commands with explicit demo/live adapters. Test cross-role denial, retries and concurrent actors.

### [DOCTOR-02] Select and scope the active practice before publishing schedules

- **Evidence:** types/doctor.ts:38 is global schedule; ProfileScreen.tsx:242 updates one hospital string; directory.ts:243 is N:M; ScheduleScreen.tsx:115 uses zero-based weekdays against scheduling.ts:90 ISO constraint. Full app paths are listed above.
- **Impact:** Direct form persistence could target wrong facility/day and cannot represent recurrence versions/exceptions.
- **Effort:** L.
- **Risk:** HIGH — bookings and availability.
- **Confidence:** HIGH.
- **Fix sketch:** Practice selector, weekday adapter, effective version/publication and leave/break controls; separately decide channel allocation and visit modes.

### [DOCTOR-03] Replace two-state appointments with lifecycle projections

- **Evidence:** `apps/doctor-mobile/src/types/doctor.ts:21`; appointments.ts:73; queue.ts:94; `apps/doctor-mobile/src/features/patients/screens/ScanQrScreen.tsx:157` fabricates lookup appointments.
- **Impact:** Pending/rejected/cancelled/no-show and called/held/arrival workflows have no working controls; scan is not check-in.
- **Effort:** L.
- **Risk:** HIGH — queue/capacity and clinical workflow integrity.
- **Confidence:** HIGH.
- **Fix sketch:** Distinct state DTOs and transactional commands, approval/queue controls for solo doctor too, server-resolved appointments.

### [DOCTOR-04] Align clinical entry with signed revisioned records

- **Evidence:** prescriptions.ts:132 requires fields absent from `apps/doctor-mobile/src/features/prescriptions/screens/PrescriptionScreen.tsx:217`; clinical.ts:158 supports corrections; store :66 only flips completion.
- **Impact:** Required clinical data cannot be faithfully populated, and amendments/discontinuation are inaccessible.
- **Effort:** L.
- **Risk:** HIGH — clinical correctness.
- **Confidence:** HIGH.
- **Fix sketch:** Structured entry, versioned signing and amendment UI, clinician-only commands; keep unsigned local drafts separate from immutable published records.

### [DOCTOR-05] Resolve service fulfilment data and provider boundaries

- **Evidence:** types/doctor.ts:1 has three modes; HomeVisitScreen.tsx:25/:143 requires address/challenge; ChatScreen.tsx:82 is local; OnlineConsultationScreen.tsx:18 is local state; directory.ts:281 has generic services only.

- **Risk:** HIGH — sensitive data and integration choices.
- **Confidence:** HIGH.
